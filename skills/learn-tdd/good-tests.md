# 什么是好测试（给新手看的版本）

## 一句话标准

**好测试测的是「用起来对不对」，不是「里面怎么写的」。**

代码内部可以整个推倒重写，测试不应该跟着改。如果你重构了一下、逻辑完全没变、测试却红了，那是测试写错了，不是代码写错了。

## 好测试长什么样

```ts
// ✅ 好：测的是行为，名字读起来像需求
it("购物车为空时，总价是 0", () => {
  const cart = createCart();
  expect(cart.total()).toBe(0);
});

// ✅ 好：期望值是手写的具体数字
it("两件 30 元的商品，总价 60 元", () => {
  const cart = createCart();
  cart.add({ price: 30 });
  cart.add({ price: 30 });
  expect(cart.total()).toBe(60);
});
```

## 三种新手最常踩的坑

### 1. 自己算给自己看（同义反复）

```ts
// ❌ 坏：期望值是把代码逻辑重算了一遍
expect(add(a, b)).toBe(a + b);
```

这个测试永远会通过，哪怕 `add` 写成了减法（只要你把断言也写成减法）。期望值必须来自**独立的事实**：手算出来的数、需求文档里的例子、一个你确定的已知结果。

### 2. 伸手进去摸内部

```ts
// ❌ 坏：测私有状态，而不是对外行为
expect(cart._items.length).toBe(2);

// ✅ 好：通过对外的方法观察
expect(cart.itemCount()).toBe(2);
```

前者的问题：哪天把 `_items` 改名叫 `_lines`，测试立刻红，但功能一点没坏。测试变成了改代码的阻力，而不是保护网。

### 3. 一口气写十个测试再去实现

新手常见冲动：把能想到的情况全列出来，写十个测试，然后开始实现。

问题在于，这十个测试测的是**你想象中**的行为。等你真的写实现，会发现有三个场景根本不存在、有两个参数形状不对。改测试比改代码更烦。

正确做法是**一次一片**：写一个测试 → 实现它 → 再写下一个。每个测试都建立在上一轮学到的东西之上。

## 一个测试该测多少

一个测试测**一件事**。测试名里如果出现「并且」「同时」，通常意味着该拆成两个。

```ts
// ❌ it("能添加商品并且能计算总价并且能清空", ...)
// ✅ it("添加商品后，商品数量增加", ...)
// ✅ it("添加两件商品后，总价是它们的和", ...)
```

失败的时候你会感谢自己：一个只测一件事的测试变红，你立刻知道坏的是哪件事。
