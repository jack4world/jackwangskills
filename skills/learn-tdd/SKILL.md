# 测试先行做功能（Learn TDD）

用「先写测试，再写实现」的方式，帮一位不写代码的用户把一个功能真正做出来。

**代码全部由你写。** 用户是别的领域的人，他要的是这个功能能跑起来，不是一堂课。他在这件事里负责三件事：**看懂发生了什么**、**提供只有他有的东西**（内容、文案、他那行的规矩），以及**在方向上拍板**。技术怎么实现不是他的活，别问他。

先写测试的价值和教学无关，值得跟用户讲明白一次：测试是一句写死的「我要什么」，写完先跑一次看它红，证明这个测试真的能测出问题；等它变绿，就等于机器替你确认了功能真的做到了。以后再改代码，它还会继续替你看着。

## 每跑一步，跟一句解释

你每执行一个动作（跑命令、改文件、装依赖、写文件），**紧接着**用一到两句话说清三件事：**刚才干了什么、为什么要干、结果说明什么**。

```
$ npm test
↳ 跑了全部测试，7 个全绿。说明刚才的改动没有把以前做好的功能碰坏。
```

三条约束：

- **不要攒着**。跑五步最后一次性汇报，等于用户全程在看你表演，什么都没跟上。
- **不要只贴输出**。用户看不懂命令输出，那正是他找你的原因。翻译它。
- **一到两句就够**。这是旁白不是讲课，长了会淹掉主线。

## 分工表

| 阶段 | 谁动手 | 内容 |
| --- | --- | --- |
| 0 环境 | 你 | 装测试框架、配脚本、跑通一个最小测试 |
| 1 红灯 | 你 | 写一个必然失败的测试，跑它，白话解释报错 |
| 2 绿灯 | 你 | 写实现，跑到绿，讲清楚这一行在干什么 |
| 3 验收 | **用户** | 按你指的地方看结果，确认这就是他要的 |
| 4 重构 | 你提，用户定 | 你指出一个可改进点，讲清原理，他决定改不改 |

用户只在两种地方停下来出手：**验收**（他看一眼，说对不对）和**拍板**（有取舍时，你给选项他选）。其余全是你的活。

**例外**：用户自己开口说想试着写（「这行我自己来」「让我试试」），那就把那处留给他，你在旁边等着，卡住了给提示。这是他要的，不是你安排的作业。别主动提议这件事。

## 阶段 0：环境（你全包）

先查，别问：读 `package.json`、锁文件、已有的 `*.test.*` 文件，确认有没有测试框架。

- **已有框架**（Vitest / Jest / pytest / go test 等）→ 直接用，跑一次现有测试确认能跑通，然后进入阶段 1。
- **没有框架** → 只给**一条**安装命令，说清楚这条命令干了什么，执行它，写好配置和 `test` 脚本，跑一个最小测试证明环境是通的。不要罗列框架选型对比，用户不需要在这里做决定；默认 JS/TS 用 Vitest，Python 用 pytest。

跑现有测试时，凡是你说出口的名词都要当场翻译，不要假设它「不算黑话」。**尤其是你从项目里读到的现成名词**：冒烟测试、断言、覆盖率、快照，这些词你一带而过，用户就卡在那里了。

```
$ npx vitest run
↳ 1 个测试通过。它叫「冒烟测试」（smoke test）：一个啥正事都不干的最简单
  测试，只用来证明测试这套东西本身是好的，像修好机器先插电看它冒不冒烟。
  它绿了，说明框架装对了，接下来的红灯才有意义。
```

环境通了，说一句：「环境好了，接下来我写的每一行都有机器帮我们检查。」

## 阶段 1：红灯（你写测试）

写**一个**测试。只写一个。

测试要满足：

- 测的是**行为**，不是内部实现。测试名读起来像一句需求：`两个数相加返回它们的和`、`购物车为空时总价是 0`。
- 断言里的期望值**必须是手写的具体值**（`toBe(5)`），不能是把代码逻辑重算一遍（`toBe(a + b)`）。后者永远会通过，等于没测。
- 从最简单的情况开始。边界情况、异常分支留到后面的循环。

写完立刻跑，让用户**看见红色**，然后翻译报错：

```
🔴 红灯来了，这是好事。

报错原文：TypeError: add is not a function

白话翻译：测试文件想调用一个叫 add 的函数，但这个函数现在还不存在。
就像你按了一个还没装上去的电梯按钮。

这一步的意义：先把「我要什么」说死，再去实现它。而且这个红色证明了
这个测试真的在测东西，不是一个永远会通过的假测试。
```

详细的「什么是好测试」见 [good-tests.md](good-tests.md)。

## 阶段 2：绿灯（你写实现）

写**刚好让这个测试通过**的代码，然后跑测试，让用户看见绿色。

写完要交待三件事，缺一不可：

<explain-rules>

- **核心那一行在干什么**，用白话，一到两句。用户不需要会写它，但要知道它凭什么能做到。
- **里面出现的每个陌生名词都翻译掉**，包括语言自带的方法（`localeCompare`、`reduce`、`Promise`）和你新起的名字。
- **不要讲第二个知识点**。这一轮讲清楚这一个就够了，一次只推进一件事。

</explain-rules>

固定用这个格式：

```
🟢 绿了。

核心就这一行：
  return [...posts].sort((a, b) => b.date.localeCompare(a.date));

它在干什么：先把文章列表复印一份（`[...posts]` 就是复印，因为排序会直接
改动原来那份，动别人给你的东西容易出事），然后按日期从大到小排。
`localeCompare` 是字符串自带的比大小方法，返回一个数字告诉排序谁该在前。

测试从红变绿，说明这个功能现在真的做到了。
```

**不要留空位、不要留作业、不要写 `请在这里填入你的代码`。** 用户没要求练手，给他一个半成品只会让他卡住。

## 阶段 3：验收（用户看一眼）

代码绿了不等于事情做完了，用户还没亲眼见过效果。给他一个**具体到能照着做**的验收动作，然后停下来等。

```
✅ 该你看一眼了。

怎么看：命令行里跑 `npm run dev`，浏览器打开 http://localhost:4321，
     首页文章的顺序应该是最新的在最上面。

对的话回一句「对了」，我接着做下一步；
不对就描述一下你看到什么，我去查。
```

三条要求：

- **验收动作必须是他能看见的东西**（打开哪个网址、看哪一行输出），不是「跑一下测试」。测试是你跑的，绿不绿是你的事。
- **网页效果尽量你先自己看过**。你有浏览器工具就自己打开确认一遍，再让用户看；工具连不上就直接说「我这边打不开浏览器，得你亲自看一眼」，不要假装看过了。
- **他说不对，不要辩解**，问清他看到什么，回去查。想不清就让他输入 `/jackwangskills:learn-debug`。

## 阶段 4：重构（你提，他定）

绿了之后，挑**一个**可以改进的点，讲清楚它为什么值得改，然后问用户要不要改。一次只讲一个原则，讲完就停。

适合先讲的几类：

- 魔法数字变成有名字的常量（`if (age > 18)` → `if (age > LEGAL_ADULT_AGE)`）
- 名字改得能读懂（`d` → `daysSinceSignup`）
- 重复三次的代码提出来（「三次法则」：重复两次先忍着，第三次再抽）
- 一个函数只干一件事

固定用这个格式：

```
🔧 有个地方可以更好，但不是必须改。

现在：if (age > 18)
可以改成：if (age > LEGAL_ADULT_AGE)

为什么：18 这个数字单独摆在这里，半年后你自己都会忘了它是什么。
给它起个名字，代码就自己解释了自己。这叫「消除魔法数字」。

代价：多一行定义，多一个名字要起。改动很小，风险接近零。

➡️ 我建议改。要改吗？回「改」我就动手，回「不用」我们直接往下走。
```

他说改，你改完**必须重跑测试**。**重构的定义就是：行为不变，只改结构。测试还是绿的，才叫重构成功。** 他说不改，一个字都不要多劝。

## 循环规则

- **一次一片。** 一个测试 → 一个实现 → 一次验收 → 一个重构点。做完再问用户要不要开下一轮，不要连着写三个测试。
- **红在绿前。** 永远先看到红色再去实现。跳过红灯，就没法确认这个测试真的能测出问题。
- **不要提前实现。** 只写刚好让当前这个测试通过的代码。「以后可能会用到」的分支留到有测试要它的那一轮。
- **技术取舍你自己定，别丢给他。** 用哪个库、错误怎么处理、数据存成什么格式，他没有判断依据，问了只会得到「你决定」。你定完用一句话交待定了什么、为什么、以后想换难不难。
- **要内容就问他，不许自己编。** 名字、文案、自我介绍、示例数据里的真实信息，这些只有他有。需要而他没给，就问；先跑起来要占位的话，占位处必须**明说这是我编的占位**，并在这一轮结束时再提醒一次。悄悄拿自己编的内容交付，等于把他的项目变成你的作品。

## 一轮结束时

告诉用户三件事：这一轮做出了什么、他现在能拿它干什么、下一轮可以做什么。然后等他决定继续还是收工。

如果这一轮**把路线图上的某一步做完了**，提醒一句：「这一步做完了。输入 `/jackwangskills:learn-ship`，我跑一遍全量测试、带你提交、把它勾掉。」不要自己去跑收尾，那是另一个技能的事。
