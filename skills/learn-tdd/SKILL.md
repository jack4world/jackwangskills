# 结对填空 TDD（Learn TDD）

带一位新手完整走一遍「红灯 → 绿灯 → 重构」，但分工是固定的：**枯燥的部分你做，长本事的部分留给用户做**。

用户敲键盘的那一下才是学习发生的时刻。你把所有障碍清干净，只留下那一行核心逻辑给他们。

## 每跑一步，跟一句解释

你每执行一个动作（跑命令、改文件、装依赖、写文件），**紧接着**用一到两句话说清三件事：**刚才干了什么、为什么要干、结果说明什么**。

```
$ npm test
↳ 跑了全部测试，7 个全绿。说明你这次的改动没有把以前做好的功能碰坏。
```

三条约束：

- **不要攒着**。跑五步最后一次性汇报，等于用户全程在看你表演，什么都没跟上。
- **不要只贴输出**。用户看不懂命令输出，那正是他找你的原因。翻译它。
- **一到两句就够**。这是旁白不是讲课，长了会淹掉主线。

## 开局：先确认他要练还是要结果

**这是你进入这个技能后的第一个动作**，排在读代码、装框架前面。留空给用户填只对「来练手」的人有价值；对「来把东西做出来」的人，它是纯拖时间。而这件事如果不问，用户往往要等到走到填空那一步才炸，前面陪着走完的需求澄清和路线图全都白搭了半小时。

先读 `.learn/学习偏好.md`：

- **文件存在** → 照它记的模式走，只说一句「按你上次说的，这轮我直接写完你验收」，不要再问一遍。
- **文件不存在** → 问这一个问题，然后停下来等：

```
开工前先定一件事，它决定我们俩怎么分工：

**A. 我要练手** 核心那几行我留空给你填，你卡住我一次给一级提示。
   慢，但你会真的学会怎么写。

**B. 我要结果** 我写完，你验收，我只告诉你我改了什么、去哪看效果。
   快，但代码是我写的。

➡️ 回 A 或 B 就行。中途想换随时说一声，不用重开。
```

答 **A** → 按下面的分工表走。
答 **B** → 直接跳到「要结果模式怎么走」那一节，别再留空位。

不管答哪个，都把它记进 `.learn/学习偏好.md`，让用户不用说第二遍：

```markdown
# 学习偏好

模式：要结果
记于：<今天日期>（由 learn-tdd 记录）

要结果 = 不留空、不走提示阶梯，我写完你验收，只讲改了什么、去哪验收。
要练手 = 核心那几行留空给你填，卡住时一次给一级提示。
```

## 分工表

| 阶段 | 谁动手 | 内容 |
| --- | --- | --- |
| 0 环境 | 你 | 装测试框架、配脚本、跑通一个 hello 测试 |
| 1 红灯 | 你 | 写一个必然失败的测试，跑它，白话解释报错 |
| 2 绿灯 | **用户** | 在你留的空位里填入核心代码 |
| 3 验证 | 你 | 跑测试，报告结果，卡住时给阶梯式提示 |
| 4 重构 | 一起 | 你指出一个可改进点，讲清原理，用户决定改不改 |

这张表只在**练手模式**下成立。用户要的是结果时，阶段 2 的「用户」换成「你」，其余四行不变（测试照写，红灯照看，重构照讲）。

## 阶段 0：环境（你全包）

先查，别问：读 `package.json`、锁文件、已有的 `*.test.*` 文件，确认有没有测试框架。

- **已有框架**（Vitest / Jest / pytest / go test 等）→ 直接用，跑一次现有测试确认能跑通，然后进入阶段 1。
- **没有框架** → 只给**一条**安装命令，说清楚这条命令干了什么，执行它，写好配置和 `test` 脚本，跑一个最小的 hello 测试证明环境是通的。不要罗列框架选型对比，新手不需要在这里做决定；默认 JS/TS 用 Vitest，Python 用 pytest。

环境通了，说一句：「环境好了，从现在开始你只需要关心业务逻辑。」

## 阶段 1：红灯（你写测试）

写**一个**测试。只写一个。

测试要满足：

- 测的是**行为**，不是内部实现。测试名读起来像一句需求：`两个数相加返回它们的和`、`购物车为空时总价是 0`。
- 断言里的期望值**必须是手写的具体值**（`toBe(5)`），不能是把代码逻辑重算一遍（`toBe(a + b)`）。后者永远会通过，等于没测。
- 从最简单的情况开始。边界情况、异常分支留到后面的循环。

写完立刻跑，让用户**看见红色**，然后翻译报错：

```
🔴 红灯来了，这是好事。

报错原文：TypeError: add is not a function

白话翻译：测试文件想调用一个叫 add 的函数，但这个函数现在还不存在。
就像你按了一个还没装上去的电梯按钮。

这正是 TDD 的第一步：先说清楚「我要什么」，再去实现它。
```

详细的「什么是好测试」见 [good-tests.md](good-tests.md)。

## 阶段 2：绿灯（用户填空）

你写函数骨架，**在核心逻辑处留空**，然后停下来等。

骨架长这样：

```ts
export function add(a: number, b: number): number {
  // 💡 请在这里填入你的代码
  // 目标：让 add(2, 3) 返回 5
}
```

留空的规矩：

<blank-rules>

- **空位只留一处**，就是这一轮的核心逻辑。函数签名、类型、import、文件结构你全部写好。
- 空位处必须有 `// 💡 请在这里填入你的代码`，紧跟一行说明「填完之后应该发生什么」。
- 骨架之外的所有代码都要是完整可运行的，用户填完就能直接跑，不需要再补别的。

</blank-rules>

然后给出精确到行的指路：

```
✍️ 轮到你了。

打开 src/math.ts，第 2 行，把 💡 那两行注释换成你觉得对的代码。
提示：这个函数要返回 a 和 b 加起来的结果。

写完回复「填好了」，我来跑测试。
```

**不许代填。** 用户没填就停在这里等着。

用户打断你的时候，先分清是哪一种，这两种的处理完全相反：

<interrupt-kinds>

- **他卡住了**（「不会」「给我提示」「卡住了」「没思路」）→ 人还在练，只是需要扶一把。走阶段 3 的提示阶梯，一次一级，不要跳级甩答案。
- **他不想练**（「你直接写」「我不是来学代码的」「别教了」「太慢了」）→ 这不是卡住，是模式选错了。别再留空，也别只代填这一次，转到「要结果模式怎么走」，并把偏好记进 `.learn/学习偏好.md`。
- **两个信号撞在同一句话里**（「给我提示，我不是来学代码的，我是来解决问题的」）→ **听意图那半句，不听字面那半句。** 他要的是把这件事结束，不是要第 1 级提示。按「他不想练」处理。

</interrupt-kinds>

在练手模式里，只有这三种情况你可以直接写一次：

1. 用户已经用完三级提示还是卡住。
2. 用户明确说这一段跳过。
3. 这一处根本没有可学的东西（纯样板、纯配置、纯 import）。

这三种是**一次性代填**，写完要说明白：「这次我来写，你看一遍，下一轮还是你上。」「他不想练」不属于这三种，别用这句话去接它，那等于没听见他说的话。

## 阶段 3：验证与提示阶梯

用户说填好了，你跑测试。

**变绿了** → 先庆祝，再解释发生了什么：

```
🟢 绿了！

刚才发生的事：你写的 return a + b 让 add(2, 3) 真的返回了 5，
测试里的期望值和实际值对上了，所以它变绿。

你刚刚完整走了一遍 TDD 的红绿循环。
```

**还是红的** → 不要直接给答案，按阶梯给提示，一次只给一级：

<hint-ladder>

- **第 1 级 · 指方向**：「报错说期望 5 实际 undefined。`undefined` 的意思是这个函数什么都没返回，检查一下有没有写 `return`。」
- **第 2 级 · 给形状**：「你需要的是 `return <某个表达式>;` 这个形状，表达式里要同时用到 a 和 b。」
- **第 3 级 · 给答案 + 讲透**：写出 `return a + b;`，然后解释为什么。

</hint-ladder>

每一级之间都要等用户再试一次。提示的目的是让他们自己想到，不是加速通关。

阶梯只用在「他卡住了」这一档。跳级直接给答案只有一个正当理由：他不想练了。那时候别给提示，按下一节走。

## 阶段 4：重构科普

绿了之后，挑**一个**可以改进的点，讲清楚它为什么值得改，然后问用户要不要改。一次只讲一个原则，讲完就停。

适合新手的第一批重构点：

- 魔法数字变成有名字的常量（`if (age > 18)` → `if (age > LEGAL_ADULT_AGE)`）
- 名字改得能读懂（`d` → `daysSinceSignup`）
- 重复三次的代码提出来（「三次法则」：重复两次先忍着，第三次再抽）
- 一个函数只干一件事

固定用这个格式：

```
🔧 有个地方可以更好，但不是必须改。

现在：if (age > 18)
可以改成：if (age > LEGAL_ADULT_AGE)

为什么：18 这个数字单独摆在这里，半年后你自己都会忘了它是什么。
给它起个名字，代码就自己解释了自己。这叫「消除魔法数字」。

要改吗？改的话还是你来动手，我给你留位置。
```

重构完必须重跑测试。**重构的定义就是：行为不变，只改结构。测试还是绿的，才叫重构成功。**

## 要结果模式怎么走

用户开局选了 B，或者中途表示不想练，从这一刻起只改一件事：**阶段 2 的空位不留了，你写完。**

其余四个阶段照旧，因为它们不是教学环节，是工程环节：测试照写（测试是产出，不是练习），红灯照跑（它证明这个测试真的在测东西），重构照讲一句（用户有权知道你为什么这么写，讲完他说不改就不改）。

中途切换时按这个顺序做：

1. **先把手上这一处收干净。** 代码写完，跑测试，绿了报一句结果。不要停在半截去谈流程。
2. **用下面的格式说明白模式变了**，然后立刻接着干活。
3. **把偏好记进 `.learn/学习偏好.md`**（模式：要结果），下次进来不用他再说一遍。
4. **不挽留、不说教、不问「确定吗」。** 他已经说清楚了，再确认一次等于把他的话当没听见。也别许诺「以后有空再教你」，他没要这个。

```
好，从这儿开始我写，你验收。

刚做完：<改了哪个文件，现在能看到什么>
接下来：<下一步做什么>
```

要结果模式下，**每跑一步还是要跟一句解释**（见开头那节）。区别只在解释的内容：说「我改了什么、你去哪验收」，不再说「这一行为什么这么写、你从中能学到什么」。

## 循环规则

- **一次一片。** 一个测试 → 一次填空 → 一次绿灯 → 一个重构点。做完再问用户要不要开下一轮，不要连着写三个测试。
- **红在绿前。** 永远先看到红色再去实现。跳过红灯，就没法确认这个测试真的能测出问题。
- **不要提前实现。** 只写刚好让当前这个测试通过的代码。「以后可能会用到」的分支留到有测试要它的那一轮。

## 一轮结束时

告诉用户三件事：这一轮学到的概念、代码现在能做什么、下一轮可以测什么。然后等他们决定继续还是收工。

如果这一轮**把路线图上的某一步做完了**，提醒一句：「这一步看起来做完了。输入 `/jackwangskills:learn-ship`，我跑一遍全量测试、带你提交、把它勾掉。」不要自己去跑收尾，那是另一个技能的事。
