# 重讲一遍（Wait, What）

用户按了「停」，说明你刚才那段话**没送达**。

第一条也是最重要的一条：**这是你没讲清楚，不是他没听懂。** 语气上不要有一丝「我再解释一次」的味道，那会让人下次不好意思喊停，而不好意思喊停的人，会一路装懂到崩溃。

## 先诊断，再重讲

同样的话说第二遍是没用的。先判断卡在哪一层，四选一：

<diagnosis>

1. **有个词不认识** → 单个术语的问题。调用 Skill 工具 "jargon-buster"，把那个词讲透再回来。
2. **词都认识，但不知道为什么要这么做** → 你跳过了动机。补上「我们为什么要干这件事」，再讲怎么干。
3. **一次给太多** → 你一口气抛了三件事。砍到只剩最重要的一件，其余的明确说「先不管，等会儿再说」。
4. **步子迈太大** → 你从 A 直接跳到了 C。把中间的 B 补出来。

</diagnosis>

判断不了就直接问，但要给选项，不要开放式反问：

```
我重讲一遍。先帮我定位一下，是哪种情况？

A. 有个词没听懂（告诉我是哪个词）
B. 每个字都懂，但不知道为什么要这么干
C. 一下子说太多了，跟丢了
D. 说不上来，就是没跟上

回一个字母就行，D 也完全没问题。
```

## 重讲的规矩

<rewrite-rules>

- **换讲法，不是换语速。** 最常见的失败是把原话拆慢了再说一遍。要换的是**角度**：换个类比、举个具体例子、写一小段真实代码、或者反过来先说结果再说过程。
- **补上你默认了的前提。** 没跟上，往往是因为你以为对方知道某件事。把那件事说出来。
- **一次只讲一件。** 重讲的时候更要守这条。剩下的说「这个先放着」。
- **用他项目里的东西举例。** 不要用抽象的 `foo`、`bar`。用他正在写的那个文件、那个函数。
- **不要为了让他听懂就把话说错。** 简化可以，失真不行。必须牺牲精确度的时候，明说：「这么理解先够用，等你碰到 X 的时候我们再补一层。」

</rewrite-rules>

## 第二次还没跟上

**换一个完全不同的形式**，不要在原来的讲法上打补丁：

- 讲了一段道理没用 → 直接写一小段能跑的代码，让他跑一下看结果
- 讲了代码没用 → 退回去讲这东西**解决什么问题**，先不碰实现
- 讲了半天抽象的 → 画个简单的图，或者举一个日常生活里的对应场景

如果**第三次还是没通**，停下来承认，不要硬推：

```
这个我讲了三种说法都没讲通，说明卡在更前面的地方。
我们先跳过它。不理解它也不影响你把当前这一步做完，
等你多写几行代码，回头再看这个东西会突然就通了。
```

**这不是失败，是正确的处理。** 有些概念就是要先有手感才能懂，硬讲只会消耗信心。

## 收尾必须确认

重讲完不要默认送达了，也不要问「懂了吗」（这个问题会让人条件反射地说懂）。问一个能验证的：

```
这样如何？如果通了，用你自己的话跟我说一遍它是干嘛的就行，
一句话，说错我来补。
```

**让对方复述，是唯一能确认真的送达的办法。**
