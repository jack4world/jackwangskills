# 报错诊断（Learn Debug）

新手 80% 的时间花在报错上，也正是在这里最容易被 AI 一把包办、什么都学不到。

这个技能的规矩：**报错先翻译，重现先建立，猜测先排序，修完必复盘。**

## 每跑一步，跟一句解释

你每执行一个动作（跑命令、改文件、装依赖、写文件），**紧接着**用一到两句话说清三件事：**刚才干了什么、为什么要干、结果说明什么**。

```
$ npm test
↳ 跑了全部测试，7 个全绿。说明你这次的改动没有把以前做好的功能碰坏。
```

三条约束：

- **不要攒着**。跑五步最后一次性汇报，等于用户全程在看你表演，什么都没跟上。
- **不要只贴输出**。用户看不懂命令输出，那正是他找你的原因。翻译它。
- **一到两句就够**。这是旁白不是讲课，长了会淹掉主线。

## 铁律：没有稳定重现，不许开始猜

这是整个技能的核心，也是新手最常翻车的地方。看到报错第一反应是打开代码找哪里错了，然后开始瞎改。改着改着，报错变成另一个报错，你已经不知道自己在修什么了。

**正确的顺序是反过来的**：先拿到一个「跑这条命令，它每次都错」的东西，再去想为什么。

有了稳定重现，你的每次猜测都能被验证。没有它，你只是在赌。

## 阶段 1：翻译报错（你做）

先把报错念给用户听，用白话。三件事：

```
🔴 报错在说什么

原文：TypeError: Cannot read properties of undefined (reading 'title')

白话：代码想读一个东西的 title 属性，但那个东西压根不存在（是 undefined）。
就像你去翻一个空抽屉里的文件夹。

出错的位置：src/pages/index.astro 第 14 行
```

**教会他们看报错栈**。这是能带走的技能，比修好这个 bug 值钱：

> 报错栈那一长串，**从上往下数，第一行提到你自己写的文件的那一行，才是你要看的**。上面那些都是库的内部代码，不是你的错。

第一次遇到某类报错时，顺手讲一下这类报错通常意味着什么。常见的十种见 [common-errors.md](common-errors.md)。

## 阶段 2：建立稳定重现（你做）

给出**一条命令**，跑了就能看见这个错。按这个顺序找：

<repro-ladder>

1. **一个失败的测试**。最好的形式，因为修好之后它自动变成防复发的网。
2. **一条命令**，比如 `npm test`、`npm run build`、`node script.js`。
3. **一个网址加一个操作**：「打开 http://localhost:4321，点那个按钮，就白屏」。
4. **实在没有** → 老实说没有，让用户描述他做了什么导致出错，一步步跟着走一遍。

</repro-ladder>

拿到之后**当场跑一次给用户看**，确认：

- [ ] 它错的**就是用户说的那个错**，不是附近另一个错
- [ ] 跑三次都错，不是偶尔才错

偶尔才错的（时好时坏）要特别说明：「这种最难查，因为你没法确认修好了没有。先想办法让它每次都错，再修。」

## 阶段 3：排序你的怀疑对象（你做）

给 **2 到 3 个**猜测，排好序，每个必须带一句**可验证的预测**：

```
我的排序：

1️⃣ 最可能：文章数据没读到，所以 posts 是空的
   验证方法：在第 12 行加一句打印，看 posts 到底是什么
   如果是它：打印出来会是 undefined 或者空数组

2️⃣ 次可能：读到了，但字段名拼错了（title 写成了 Title）
   验证方法：打印出来看第一篇文章的字段长什么样

3️⃣ 不太可能但要排除：文件路径写错了，读的是不存在的目录
```

**说不出「怎么验证」的猜测就不是猜测，是感觉，不要列出来。**

## 阶段 4：一次只验一个（你做）

从第 1 个开始验。**一次只改一个东西**，改完立刻跑阶段 2 那条命令。

新手最常见的翻车：同时改三个地方，然后错误消失了，但你不知道是哪个改动起了作用。下次再遇到还是不会。

验证用的临时打印语句，统一加个标记方便清理：

```js
console.log("[DEBUG]", posts);
```

修好之后**必须把这些 `[DEBUG]` 全部删掉**，搜一下这个词就能找全。

## 阶段 5：复盘（你做，不许省）

修好了不算完。最后必须讲这三句：

```
✅ 修好了。回头看一眼刚才发生了什么：

真正的原因：<一句话>

你下次怎么自己认出来：<这类报错的特征，具体到能用>
比如：看到 "Cannot read properties of undefined"，
八成是某个东西没拿到值就被使用了。先去打印那个东西本身，
而不是去研究出错的那一行。

要不要补一个测试防止它再犯？（输入 `/jackwangskills:learn-tdd`）
```

**省掉复盘，这次调试就白做了**。你只是修好了一个 bug，没学会怎么修 bug。

## 什么时候别按这套走

不要教条。如果是一眼就能看出的低级错误（少个分号、拼错单词、忘了 import），直接说：

「这个是笔误，`titel` 拼错了，应该是 `title`，第 14 行。这种错不用走完整流程，改了就行。」

把完整流程留给真的想不通的问题。对着一个拼写错误走五个阶段，是在浪费你的时间，也会让人以后不敢来问。
